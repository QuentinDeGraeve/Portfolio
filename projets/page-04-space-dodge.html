Le problème

Développer un jeu, même simple, oblige à relier des systèmes qui s'ignorent habituellement : les entrées utilisateur, la physique, le rendu visuel, l'audio, la progression et la persistance. Une mécanique qui fonctionne en isolation peut créer des bugs inattendus quand tout interagit en même temps.

Space Dodge est un terrain d'expérimentation intentionnel — l'objectif n'est pas le jeu fini, c'est de comprendre Unity par la pratique en touchant à chacun de ces systèmes.

Architecture des scènes

La fiche couvrira la structure en scènes Unity choisie :

  • Menu principal — gestion du GameManager, chargement de la scène de jeu
  • Scène de jeu — boucle principale, spawn des obstacles, gestion de la fin de partie
  • Game Over — affichage du score, accès aux meilleurs scores, retour au menu

La communication entre scènes (score, états) passe par un singleton GameManager persistant entre les chargements.

Gestion des entrées

L'Input System de Unity (nouveau système, pas le Legacy) gère les contrôles — clavier sur desktop, touch sur Android. La fiche documentera les Input Actions configurées et la gestion des différences de comportement entre les deux plateformes.

Un problème spécifique à documenter : la dead zone sur les axes tactiles et la gestion du multi-touch non intentionnel.

Score & sauvegarde

Le système de score est progressif (distance parcourue + obstacles évités). La sauvegarde utilise JSON + PlayerPrefs pour les meilleurs scores locaux. La fiche comparera cette approche à ScriptableObjects pour la persistance des données de jeu.

Pipeline mobile Android

La chaîne de build Android via Unity nécessite :

  • Configuration du module Android dans Unity Hub
  • Keystore pour la signature de l'APK
  • Réglage des paramètres graphiques (tier de qualité, résolution adaptative)
  • Test sur appareil physique via ADB

Des captures réelles du jeu en cours et les corrections apportées aux effets visuels Android viendront remplacer cette illustration de travail.

Limites

Un prototype personnel implique des compromis assumés : pas de tests automatisés (Unity Test Framework non utilisé), gestion mémoire basique (pas de pool d'objets pour les obstacles), effets visuels désactivés sur les appareils de bas de gamme. Ces choix seront documentés et justifiés.
